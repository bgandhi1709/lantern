# Actions go through a Service Bus queue to Lantern.Functions

Work the API must not do inside a request, starting with deleting a Child (ADR-0003), is event driven: the API puts a typed message on one Azure Service Bus queue, `workspace-events` (Bicep passes its name to both apps as `Actions__Queue`; the trigger reads `%Actions:Queue%`), and `Lantern.Functions` handles it. There is no timer anywhere. The first version of the delete used a `BackgroundService` on a `PeriodicTimer`; it ran only while the API container was awake, and the container scales to zero (D10), so a delete that failed once waited for the next request.

The message carries an id, a `type` (`create-workspace`, `remove-workspace`) and a JSON payload. One Functions trigger hands every message to a dispatcher, which picks an `IActionHandler` by type through DI. The dispatcher and the handlers live in `Lantern.Functions/Handler`; the API only records and sends. A new action is a new handler and a new type, not a new queue, trigger or deployment. A type moves to its own queue only if it needs its own scaling or priority.

The queue and the table cannot commit together, so the API writes first and sends second. Each action has a row in the `actions` table of the existing storage account (partition is the type, row key is the action id). That row is the commit point and the idempotency record: repeating a request is the same row, the handler does nothing for a message whose row is gone, and the handler deletes the row last. If the send fails the request still succeeds, and a one-shot pass when the API starts sends again any action whose row was last sent more than five minutes earlier. Handlers must be safe to repeat, because a message can arrive twice.

Retries are the queue's. The Function settles a message itself: it completes it on success, dead-letters one that can never succeed (an unknown type, a body that is not an action), and leaves a failed one unsettled, so the five-minute lock expiring is the retry delay. A message is dead-lettered after 288 deliveries (about a day), the row stays in the ledger and the next API start sends it again, so a hard delete is never abandoned.

`Lantern.Functions` is an Azure Functions app (isolated worker) packaged as its own image and run as its own Container App in the same environment as the API. A KEDA `azure-servicebus` rule wakes it when a message arrives and it scales back to zero when the queue is empty. The API and the Functions app release independently. Both sign in with the one managed identity and role assignments (Service Bus Data Sender and Receiver); no connection string exists in Azure. Code both need (the services, the repositories, the ledger, the action types and payloads) lives in the `libs/` projects (ADR-0005); the Functions app references `Lantern.Base` and never the API.

Service Bus Basic has queues only: topics, and so publish and subscribe, need Standard. Every action has one consumer, so a queue is enough, and `IServiceBusService` (which sends any model to a named queue) is the seam if a second consumer of the same event ever appears. Basic bills about $0.05 per million operations, so 3,000 messages cost about ₹0.05 a month (at ₹88 to the dollar; list prices to be confirmed against Azure pricing). The Functions app idles at zero replicas, inside the Container Apps free grant, so it costs about ₹0 until it runs; keeping it warm would add about ₹380 a month. This reverses the earlier "no new Azure resource yet" choice and the lean-infra rule for this one resource, on purpose.

Locally, `deploy/local` runs the Service Bus emulator (with its SQL Server container) and the Functions app beside the API, so the Docker E2E proves a delete through the real queue. Unit tests swap `IServiceBusService` for a recording fake and deliver its messages to the real dispatcher from `Lantern.Functions`.

Considered and rejected: Standard with a topic now (about ₹860 a month for no second consumer), Storage Queues (the user chose Service Bus), running the receiver inside the API container with a KEDA rule (the API and the long sweeps then share CPU and a release), the Functions app as a second container in the API's Container App (one revision, one size, and a Functions change would redeploy the API), a Functions Consumption plan (the user wants it inside Container Apps), an outbox that republishes on a timer (a timer again), and sending before writing the ledger row (a message could outlive a request that then fails).
